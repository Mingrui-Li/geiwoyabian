# 多窗口开发与集成策略

## 1. 目标

这套策略解决四个问题：

1. 新窗口不知道从哪里继续。
2. 多个窗口重复开发或覆盖彼此修改。
3. 聊天中形成的决定没有沉淀，后续窗口重新争论。
4. 阶段性原型被误当成完整产品终点。

仓库文件和 Git 历史是事实来源，聊天记录只用于当次协作。

## 2. 文档职责

| 文件 | 职责 | 谁更新 |
|---|---|---|
| `AGENTS.md` | 所有窗口必须遵守的仓库规则 | 当前任务执行窗口 |
| `docs/START_HERE.md` | 新窗口固定入口 | 当前任务执行窗口 |
| `docs/STATUS.md` | 当前阶段、下一动作、已完成状态 | 当前任务执行窗口在完成时更新 |
| `docs/PROJECT_PLAN.md` | 完整产品范围与体验目标 | 产生产品决策的执行窗口更新 |
| `docs/ROADMAP.md` | 长期阶段、交付和闸门 | 阶段复盘时更新 |
| `docs/DECISIONS.md` | 已确认且会影响后续开发的决策 | 产生并验证决策的执行窗口 |
| `docs/tasks/*.md` | 单个任务的范围、依赖、验收和交接 | 对应任务执行窗口 |

优先级：仓库与测试事实 > 已确认决策 > 产品规划 > 当前状态 > 单任务说明 > 聊天记忆。发生冲突时不要默默选择；当前执行窗口必须核实事实、记录处理结果，无法安全解决时再请求用户决定。

## 3. 滚动拆解

长期范围保留在 `ROADMAP.md`，只把当前阶段和下一个阶段拆成细任务卡：

- 当前阶段：任务必须足够细，可以在一个对话中完成和验收。
- 下一阶段：只建立依赖关系和候选卡，等当前闸门通过后再补全细节。
- 更远阶段：保持路线图级别，避免早期假设制造大量过期任务。

每个阶段结束时，完成该阶段最后任务的执行窗口同时完成阶段复盘：

1. 核对闸门是否通过。
2. 将本阶段剩余问题转成明确任务。
3. 细化下一阶段任务卡和依赖。
4. 更新 `STATUS.md` 的下一动作。
5. 确认产品范围仍然是完整 v1.0。

## 4. 两种工作模式

### 模式 A：串行接力（OPC 默认推荐）

- 同一时间只有一个设计或代码任务处于 `IN_PROGRESS`。
- 可以使用多个聊天窗口，但新窗口从上一个任务卡的完成记录继续。
- 一个任务进入 `DONE` 后才解锁下一个依赖任务。
- 适合Figma设计系统、核心玩法、架构和场景集成等高耦合工作。

优点是上下文清晰、几乎没有合并冲突。多个窗口不等于必须同时编码。

### 模式 B：受控并行

只有任务卡明确标记 `parallel_safe: true` 才能并行。必须满足：

- 每个任务使用独立分支，推荐同时使用独立 Git worktree。
- 任务卡的 `edit_scope` 不重叠。
- 依赖的接口或数据结构已经合入集成分支。
- 每个执行窗口只集成自己的任务；公共状态更新前必须先同步`main`并确认没有冲突。
- 同时进行的任务建议不超过 3 个。

分支命名：`codex/gwp-<编号>-<简短名称>`。
提交信息：`feat(gwp-xxx): ...`、`fix(gwp-xxx): ...`、`docs(gwp-xxx): ...`。

不建议并行的组合：

- 两个任务都修改主场景或同一个 prefab。
- 一边重构核心状态机，一边在它上面开发玩法。
- Figma 设计未定稿时，多窗口分别实现同一个正式页面。
- 配置 schema 还在变化时批量制作关卡或物品。

## 5. 单一执行窗口职责

本项目不再设置独立审阅或集成窗口。认领任务的执行窗口必须在同一对话内完成：

- 实现任务并逐项核对验收标准。
- 运行适用的自动检查、真实环境检查和视觉QA，不得只采信完成记录。
- 将自己的任务分支合并到`main`。
- 将任务从`IN_PROGRESS`直接改为`DONE`。
- 更新`STATUS.md`、阶段看板，并把紧邻的后续依赖从`BLOCKED`解锁为`READY`。
- 处理任务之间的接口冲突。
- 确认新决策并同步相关规划文件。
- 运行跨模块构建、真机或完整回归。

验收未通过时不得标记`DONE`、不得解锁后续任务；应在当前窗口修复，或保留`IN_PROGRESS`/改为有证据的`BLOCKED`。

## 6. 单任务生命周期

```text
BLOCKED → READY → IN_PROGRESS → DONE
                       ↓
                    BLOCKED
```

### READY 前

- 依赖任务全部 `DONE`。
- 输入、输出和编辑范围明确。
- 验收可以在当前环境执行或清楚注明需要人工验证。

### IN_PROGRESS 中

- 只修改任务卡允许的范围。
- 发现范围外问题时记录，不顺手扩张任务。
- 新决策先记录候选项，不擅自改产品方向。
- 持续保护用户已有的未提交修改。

### DONE 前

- 完成任务卡所有交付物。
- 执行规定验证并记录真实结果。
- `git diff --check` 通过。
- 没有无关格式化、生成文件或 IDE 文件。
- 完成结果与风险记录。
- `main`上的构建或文档检查通过。
- 任务验收项全部满足。
- 相关决策、状态和依赖已经同步。

## 7. 冲突预防

- 任务卡必须写 `edit_scope` 和 `do_not_edit`。
- 公共协调文件仅由当前任务执行窗口在认领或完成节点更新；并行窗口不得同时改写它们。
- 新窗口启动先看 `git status`，看到不属于自己的改动就保留并绕开。
- 未提交的共享工作树不允许开启受控并行。
- 本项目的Figma写入严格串行：任何时候只能有一个Figma写任务处于`IN_PROGRESS`，不能以不同Frame为由并行执行`use_figma`变更。
- gpt-image-2 生成任务按批次和资产清单编号，候选图与已批准图分目录存放。

## 8. 决策管理

需要进入 `DECISIONS.md` 的内容：

- 会影响多个模块的技术方案。
- 会改变产品范围、玩法规则、视觉语言或内容规模。
- 难以撤销或返工成本高的选择。
- 后续窗口很可能再次提出的问题。

小型实现细节留在代码和任务卡，不把决策日志变成流水账。任何被推翻的决策保留原记录并标记 `SUPERSEDED`，不能直接删除历史。

## 9. Figma 与素材的并行边界

正式视觉工作固定分三段：

1. **素材窗口**：根据资产清单使用 gpt-image-2 生成候选素材，不设计完整页面。
2. **设计窗口**：通过 Figma MCP 建立变量、组件、屏幕和交互，筛选并组合已生成素材。
3. **实现窗口**：从精确 Figma 节点读取结构和截图，在 Cocos 中实现并做视觉对照。

三段按依赖顺序推进。全部24类界面、状态、适配、原型和Dev Handoff在Figma评审冻结前，任何Cocos初始化、灰盒、正式界面或玩法任务都不能进入`READY`。已经存在的实验分支保持隔离，设计冻结后再决定是否复用。

## 10. 阶段完成定义

阶段只有在以下条件全部满足时才结束：

- 对应路线图交付项已完成。
- 阶段闸门已实际验证，而不是主观宣布。
- 所有任务卡为 `DONE` 或明确转移到后续阶段。
- `STATUS.md` 已更新。
- 新决策已记录并同步规划。
- 集成分支可构建、可运行或通过当前阶段适用的文档检查。
